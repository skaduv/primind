# 快速问答失败后重开会话，页面报“流式连接失败: Error: HTTP 404”

**缺陷类型**：Primind 快速问答（KnowledgeQA）失败收尾，以及前端续流处理。**状态**：已修复（worktree `dsh-03f86148-29ee`，待合并），修复与复测见下方 spec。本文日期和日志时间均为北京时间（UTC+08:00）。

## 现象

打开会话「车辆管理办法与停车场规定一致性分析」，页面顶部弹出下面的报错。问题下方一直显示“正在准备回答…”，没有回答，也不会结束。

```text
流式连接失败: Error: HTTP 404
```

每次重新打开这个会话，报错都会再次出现。

![重开会话时页面报“流式连接失败: Error: HTTP 404”](images/2026-11-24-流式连接失败404.webp)

## 线上证据

会话 `01d03714-65d5-4b57-b5f3-d6f3ba0188f1` 中，同一请求 `JKkgcKCXeeNf` 写入了两条消息：

| 消息 | 角色 | 创建时间 | 状态 |
| --- | --- | --- | --- |
| `77529e5c-…` | 用户 | 2026-11-24 09:38:41 | 已完成 |
| `8bd2aeb3-6df0-46f4-8a45-dfc5aaa21fe9` | 助手，`builtin-quick-answer` | 2026-11-24 09:38:41 | **未完成**，内容为空 |

2026-11-24 15:19:21、15:19:26、15:19:30，用户三次打开这个会话。前端每次都请求续流接口，后端每次都返回 404：

```text
GET /api/v1/sessions/continue-stream/01d03714-…?message_id=8bd2aeb3-…
stream.go:124[ContinueStream] | No events found in stream
response_body={"error":"No stream events found","success":false} status_code=404
```

09:38 这次问答，就是 [OpenSearch 响应超限](2026-11-24-快速问答OpenSearch响应超限.md) 一文记录的 12 库失败请求。生产 app 容器日志从 2026-11-24 10:21 开始，09:38 的原始错误已经不在 `kubectl logs` 中。这次失败的判断依据是那篇文档的记录，加上请求时间和问题内容一致。

## 原因

下面四步依次发生，最终导致报错。

1. **快速问答失败时，助手消息没有标记完成。** 快速问答模式只在收到最终回答（`EventAgentFinalAnswer`，`Done=true`）时调用 `completeQuickAnswerTurn`，把助手消息标记为已完成。检索出错时，服务返回错误，只做两件事：释放轮次锁，发出 `EventError`。错误处理器 `handleError` 只把错误事件写进 Redis 流，不更新数据库里的消息。所以这条助手消息停在 `is_completed=false`、内容为空。Agent 模式会在 `defer` 中统一调用 `completeStreamAssistantMessage`，快速问答模式没有这一步。[完成入口](../../internal/handler/session/qa.go#L1371) · [defer 只释放锁](../../internal/handler/session/qa.go#L1457) · [失败分支](../../internal/handler/session/qa.go#L1486) · [错误事件只写流](../../internal/handler/session/agent_stream_handler.go#L630)
2. **流式事件只保留 1 小时。** Redis 流的 TTL 是 `time.Hour`。到 10:38 左右，这条消息的流事件（包括错误事件）已经过期。[TTL](../../internal/stream/factory.go#L28)
3. **前端看到未完成的助手消息，会自动续流。** 加载历史消息后，前端只要找到 `role=assistant` 且 `!is_completed` 的消息，就把它当成仍在生成，进入“正在回复”状态，然后 `GET /api/v1/sessions/continue-stream`。只有 IM 渠道的消息会改走静默轮询；网页渠道的消息续流失败后，会直接弹错误提示。[续流触发](../../frontend/src/views/chat/index.vue#L953)
4. **后端找不到流事件，返回 404。** 消息还在，但流里已经没有事件，`ContinueStream` 返回 404 `No stream events found`。前端在 `onopen` 中抛出 `HTTP 404`，`onerror` 再拼上“流式连接失败”，最后由 `watch(error)` 弹出提示。[后端 404](../../internal/handler/session/stream.go#L123) · [前端抛错](../../frontend/src/api/chat/streame.ts#L191) · [拼接文案](../../frontend/src/api/chat/streame.ts#L213) · [弹出提示](../../frontend/src/views/chat/index.vue#L1609)

如果在失败后 1 小时内重新打开会话，续流会回放流中的错误事件，用户看到的是原始错误，而不是 404。超过 1 小时，就只剩 404。由于消息永远不会变成已完成，每次打开都会重复报错，“正在准备回答…”也不会消失。

结论：**这里的 404 不是路由或权限问题，而是快速问答失败后留下的未完成助手消息造成的后果。** 直接诱因是 09:38 的 OpenSearch 响应超限，但不论快速问答因什么出错（检索、模型、超时等），之后都会出现同样的现象。

## 影响范围

- 所有在快速问答（非 Agent）模式下由服务端报错结束的会话。出错后超过 1 小时再打开，都会出现这个提示。今天侧栏中同名的多个复现会话，可能也有同样的残留消息，数量尚未统计。
- 用户无法从页面看出原始失败原因。

## 附带观察（已核实）

截图里消息时间显示为 17:38，数据库里的创建时间为 09:38，两者正好相差 8 小时。已排查：不是前端重复换算，是读库时的时区解读问题——列类型是 `TIMESTAMP WITH TIME ZONE`，服务端连接串固定 `TimeZone=UTC`，SQL 客户端看到的 `09:38` 是 UTC，对应北京时间 `17:38`，与截图一致。详见 spec §10.2。

## 修复方向（已在 worktree `dsh-03f86148-29ee` 实现）

1. 后端：快速问答的服务出错（非用户主动停止）时，把助手消息标记为已完成，并保存错误信息，与 Agent 模式在 `defer` 中统一收尾的做法保持一致。
2. 前端：续流返回 404 `No stream events found` 时，不弹“流式连接失败”。改为结束“正在回复”状态，并显示“本次回答未完成或已失败，可重新提问”。
3. 存量数据：部署后执行 `primind-server -backfill-interrupted-turns`（或 `scripts/sql/bf03_backfill_interrupted_turns.sql`）统计并修复；上线后对账任务会自动处理之后新增的残留。
