## 1. 根因与长期风险

1. **两份数据。** 编辑窗口里修改的是草稿（`formData`），共享接口读取的是数据库里已保存的配置。共享入口放在编辑窗口里，用户自然会以为"我看到的就是会被共享的"。[共享入口](../../../frontend/src/views/agent/AgentEditorModal.vue#L1802) · [共享提交](../../../frontend/src/components/AgentShareSettings.vue#L235)
2. **校验结果不具体。** 缺对话模型、缺 ReRank 都返回同一句英文提示，前端无法告诉用户具体缺什么、去哪里改。[共享校验](../../../internal/application/service/agent_share.go#L211) · [报错](../../../internal/handler/organization.go#L1405)
3. **只在共享那一刻校验。** 共享之后，如果有人清空了 ReRank 或者删除了所用的模型，已经共享出去的智能体会静默失效，接收方要到真正提问时才会碰到错误。

长期运行时，第 3 点影响最大：智能体和模型都会持续调整，而共享关系一旦建立就不会再检查配置。

## 2. 目标与非目标

**目标**

- G1：编辑窗口中有影响共享的未保存修改时，共享前给出明确提示，并提供"保存并共享"一步完成。
- G2：配置完整性检查收拢成一个函数，返回具体缺项，前端据此定位到对应字段。
- G3：同一个检查用在共享、保存（已共享时）和接收方列表展示上，让配置失效的共享智能体能被及时发现。

**非目标**

- 不改变"需要 ReRank"的判定规则（`agentRequiresRerankModel` 保持不变）。
- 不改变共享授权模型。
- 本期不实现"删除模型时自动修复引用它的智能体"，只做提示和拦截。

## 3. 兼容性约束

- C1：共享失败时的 HTTP 状态码和原有提示文案保持不变，只在 `details` 中新增机器可读的缺项列表。旧前端照常显示原来的提示。
- C2：配置完整的智能体，共享流程与改造前一致，不增加额外步骤。
- C3：已共享智能体的保存操作，本期只给警告，**不拦截**，避免影响正在使用的工作流。是否改为拦截，根据运行一段时间后的情况再定。
- C4：知识库范围为"不使用知识库"时，ReRank 允许留空（现有规则）。

## 4. 设计

### 4.1 后端：统一的完整性检查

在 `internal/application/service/agent_share.go` 旁新建 `agent_readiness.go`：

```go
type AgentReadinessIssue struct {
    Code  string `json:"code"`  // missing_chat_model / missing_rerank_model / chat_model_unavailable / rerank_model_unavailable
    Field string `json:"field"` // config.model_id / config.rerank_model_id
}

func CheckAgentReadiness(ctx context.Context, agent *types.CustomAgent, models ModelLookup) []AgentReadinessIssue
```

- 缺对话模型：`missing_chat_model`。
- `agentRequiresRerankModel(agent)` 为 true 且缺 ReRank：`missing_rerank_model`。
- 配置的模型 ID 在本空间已经不存在或已停用：`*_unavailable`（需要查询模型表；查询失败时不阻断，只记日志）。
- `ShareAgent` 改为调用这个函数。有问题时仍然返回 `ErrAgentNotConfigured`，同时附带问题列表。
- handler 返回 `NewValidationError(原文案).WithDetails({"issues": [...]})`。HTTP 状态码和文案都不变，满足 C1。

### 4.2 后端：已共享智能体的保存警告

- `UpdateAgent` 保存成功后，如果该智能体存在有效的共享关系，就执行一次 `CheckAgentReadiness`。有问题时，在响应里加上 `warnings: [{code:"shared_agent_not_ready", issues:[...]}]`。仍然保存成功（满足 C3）。
- 现有的响应里已经有 `toolWarnings` 之类的警告字段时，复用同一个字段，不另起新字段。开发时先确认现有字段名。（核对结论见第 10.1 节：现有字段只描述 allowed_tools，结构不同，最终按本条的 `warnings` 另加，原字段保持不变。）

### 4.3 后端：接收方列表标注

- 共享智能体列表接口为每一项增加 `ready: bool` 和 `issues`。只读取已有数据，不额外查询模型表（模型可用性检查放到真正使用时）。
- 前端在共享智能体列表和选择器里，对 `ready=false` 的智能体显示"配置不完整，请联系创建者"，并禁止选择。

### 4.4 前端：共享前检查未保存修改

- `AgentEditorModal` 已经通过 `useModalShell` 的表单快照判断是否有未保存修改（[快照](../../../frontend/src/views/agent/AgentEditorModal.vue#L4160) · [判断](../../../frontend/src/composables/useModalShell.ts#L53)）。向 `AgentShareSettings` 传入两个属性：`isDirty: () => boolean` 和 `saveDraft: () => Promise<boolean>`（复用现有的保存实现，但保存后不关闭窗口）。
- 点击「共享」时：
  - 没有未保存修改：直接共享（与现在一致）。
  - 有未保存修改：弹出确认框，"模型配置等修改尚未保存，共享的是已保存的配置。" 提供两个按钮：「保存并共享」（先保存，成功后再发出共享请求；保存失败就停止，不发共享请求）和「取消」。当前选择保持不变。
- 共享失败并带有 `details.issues` 时：按缺项显示中文提示（"缺少对话模型""启用知识库检索时需要 ReRank 模型""所选模型已不可用"），并提供"去设置"链接，切换到「模型配置」页并定位到对应字段。
- 保存响应中带有 `shared_agent_not_ready` 警告时：显示警告提示"该智能体已共享，当前配置会导致接收方无法使用"。

### 4.5 模型删除时的提示（排查后决定）

- 先排查：删除或停用模型时，现在有没有检查哪些智能体在引用它。
- 如果没有：在删除确认框里列出引用该模型的智能体（标出其中已共享的），由管理员确认。只提示，不拦截。具体改动在第 10 节记录后再实施。

## 10. 记录区（开发过程中填写）

记录时间 2026-11-26（北京时间）。实现在分支 `dsh-ab1d0270-3bd7`（工作树 `.agents/worktrees/dsh-ab1d0270-3bd7`，基线 `main@633ba77`），**未合并、未推送**。

### 10.1 现有保存响应中的警告字段名

是 `allowed_tools_warnings`，但它不是通用警告列表：结构是对象 `{ kept_unknown?: string[], dropped?: string[] }`，只说明保存时后端对 allowed_tools 做了什么调整（后端 `handler/custom_agent_tools.go` 的 `allowedToolsWarnings`，前端 `api/agent/index.ts` 的 `AllowedToolsWarnings`，由 `notifyAllowedToolsWarnings` 消费）。

因此没有把结构不同的内容塞进这个字段，而是按 4.2 节的设计在响应顶层另加 `warnings: [{ code, issues }]`；`allowed_tools_warnings` 原样保留。这一点与"复用同一个字段"的字面要求不同，**待确认**。如果坚持只用一个字段，需要改动 `allowed_tools_warnings` 的结构并同步前端消费方，属于兼容性变更。

### 10.2 删除或停用模型时有没有引用检查

- **删除：有，而且是拦截。** `modelService.DeleteModel` 先调用 `getModelUsageDetails`，统计引用该模型的知识库、智能体（各自的 `CountByModelID` / `ListModelUsages`）和长期记忆绑定。有引用时返回 HTTP 400、错误码 2300（`ErrModelInUse`），`details` 里列出引用者的 id、名称和绑定字段，前端用 `ModelInUseError` 渲染并可跳到智能体编辑器。它不区分引用者是否已共享。
- **停用：没有这个操作。** 模型状态只有 `active` / `downloading` / `download_failed`，由创建和下载流程维护，`UpdateModel` 不改状态。
- **一条旁路：** YAML 内置模型加载器在每次启动时会软删除 `builtin_models.yaml` 里不再声明的内置模型行（`ManagedBy = "yaml"`），不经过引用检查。配置里还留着这类模型 ID 的智能体会静默失效，这正是 `chat_model_unavailable` / `rerank_model_unavailable` 在共享时和保存已共享智能体时能拦住的一类情况。
- **结论：** 4.5 节"在删除确认框里列出引用该模型的智能体"不需要新增——删除已经被拦截并列出了引用者。可选的后续改进是在引用列表里标出已共享的智能体，本期没有做。

### 10.3 实现说明（与 spec 正文的差异）

后端：

- `AgentReadinessIssue`、缺项常量、`AgentSaveWarning` 定义在 `internal/types/agent_readiness.go`（`types.SharedAgentInfo` 要引用它，放在 service 包会形成循环依赖）；`service/agent_readiness.go` 里用类型别名保留 4.1 节的 `service.AgentReadinessIssue`。
- `ModelLookup` 是只含 `GetByID(ctx, tenantID, id)` 的窄接口，`interfaces.ModelRepository` 直接满足。`NewAgentShareService`、`NewCustomAgentService` 各多一个 `interfaces.ModelRepository` 参数，容器里已经提供这个类型。
- T2：`ShareAgent` 返回 `*service.AgentNotReadyError`，它 `Unwrap` 到 `ErrAgentNotConfigured`，所以现有的 `errors.Is` 判断不变；handler 用 `errors.As` 取出缺项放进 `details.issues`。状态码 400、错误码 1010 和文案都没变。
- T3：新增 `customAgentService.SharedAgentReadinessIssues`，handler 通过一个可选的窄接口调用它，服务层没有实现时不报警告。"存在有效的共享关系"与已有的 `checkSharedAgentKBScope` 用同一口径：本空间作为源空间共享出去的记录。内置智能体不检查（它们的共享对接收方从不解析）。
- T4：`sharedAgentInfo` 里用 `CheckAgentReadiness(ctx, agent, nil)`，不查模型表，三个共享列表接口（`/shared-agents`、`/organizations/:id/shared-agents` 及批量）都带上 `ready` / `issues`。

前端：

- **确认框的位置**：做在"共享到共享空间"弹层内部——点「共享」后，弹层里显示"模型配置等修改尚未保存，共享的是已保存的配置。"，按钮变成「保存并共享」「取消」，上方的共享空间选择保持可见。没有另开模态框，因为点击模态框会让这个弹层先关闭，"当前选择可见"就保证不了。换了共享空间，确认状态自动失效。
- **缺项提示**：共享被拒且带 `details.issues` 时，面板顶部显示「无法共享：缺少对话模型」这类提示和「去设置」按钮，同时关掉添加弹层给提示让位；不带缺项的失败仍显示原来的提示。「去设置」通过 `configure` 事件交给编辑器，复用已有的字段高亮机制（`config.model_id` → 对话模型，`config.rerank_model_id` → ReRank 模型）。`shareAgent` 接口失败时保留服务端的 `error` 体。
- **保存警告**：`handleSave` 拆成 `saveAgentForm(close)`，「保存并共享」走 `saveDraft()`（不关窗口，保存成功后把表单快照记为已保存）。保存响应带 `shared_agent_not_ready` 时提示"该智能体已共享，当前配置会导致接收方无法使用"。
- **接收方**：`AgentSelector` 对 `ready === false` 的共享智能体显示"配置不完整，请联系创建者"，选中时只发出未就绪事件（带具体缺项），不选中；`AgentList` 的两处卡片显示同样的标签，详情抽屉禁用「在对话中使用」。本空间自己共享出去的智能体若不完整，显示"配置不完整，接收方无法使用"。旧后端不带 `ready` 时沿用原来的本地判断。
- **文案**（待确认）：`organization.share.*`（`unsavedBeforeShare`、`saveAndShare`、`notReadyToShare`、`goConfigure`、四个 `issue*`、`sharedNotReady`、`mineNotReady`）和 `agentEditor.tools.sharedNotReadyWarning`，六种语言都已补齐。

新增测试：`service/agent_readiness_test.go`、`handler/agent_readiness_test.go`、`utils/agent-share-readiness.test.ts`、`components/AgentShareSettings.test.ts`、`components/AgentSelector.readiness.test.ts`、`views/agent/AgentList.readiness.test.mjs`，`composables/useModalShell.test.ts` 和 `views/agent/AgentEditorModal.test.mjs` 各加了三个用例。

## 11. 风险与待确认

- R1：`isDirty` 依赖整个表单快照，可能把与共享无关的修改（例如头像、描述）也算进去。这种情况下提示"先保存"仍然是合理的，因为共享的始终是已保存的配置。
- 待确认：确认框和缺项提示的文案。
- 待确认：保存响应的警告放在新的 `warnings` 字段而不是复用 `allowed_tools_warnings`（第 10.1 节）。
- 待确认：确认框做在共享弹层内部而不是独立模态框（第 10.3 节）。
