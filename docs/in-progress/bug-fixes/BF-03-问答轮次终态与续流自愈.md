## 1. 根因与长期风险

表面原因是快速问答出错时没有把助手消息标记为完成。更深一层有三个结构性问题：

1. **消息生命周期只有一个布尔字段** `IsCompleted`（[message.go:506](../../../internal/types/message.go#L506)），没有"失败""中断"这类终止状态，也没有地方存错误原因。
2. **只有成功路径会写终态。** 快速问答只在收到最终回答时调用 `completeQuickAnswerTurn`（[qa.go:1962](../../../internal/handler/session/qa.go#L1962)）；出错分支只释放锁并发出错误事件（[qa.go:1486](../../../internal/handler/session/qa.go#L1486)），错误事件只写进 Redis，不更新数据库（[agent_stream_handler.go:630](../../../internal/handler/session/agent_stream_handler.go#L630)）。
3. **"是否还在生成"靠推断。** 判断依据是 Redis 流事件是否存在，而事件 1 小时后过期（[factory.go:28](../../../internal/stream/factory.go#L28)）。过期后，未完成的消息就无法区分"还在生成"和"早已死掉"。

长期运行时，**进程异常退出（OOM、k3s 滚动发布、节点重启）也会留下同样的残留**，Agent 模式的 `defer` 收尾在进程被杀时同样执行不到。残留消息只增不减，每次发版都可能新增一批，而每条残留都会让对应会话每次打开都报错。

## 2. 目标与非目标

**目标**

- G1：每条助手消息最终都进入明确的终态：完成、失败、已停止、已中断。
- G2：任何原因导致的失败（检索、模型、超时、持久化失败）都会写入终态和错误原因，快速问答与 Agent 两种模式使用同一套收尾逻辑。
- G3：进程被杀等收尾代码来不及执行的情况，由续流接口和后台对账两道机制自动修复，不需要人工处理。
- G4：用户打开失败的会话时，看到明确的"回答失败"或"回答中断"状态和"重新提问"入口，不再弹出"流式连接失败"。
- G5：一次性修复线上存量的残留消息。

**非目标**

- 不改变正常回答的流式协议和事件格式。
- 不实现"断点续写"（中断的回答不会从中断处继续生成）。
- IM 渠道消息现有的静默轮询逻辑保持不变。

## 3. 兼容性约束

- C1：`is_completed` 字段保留且语义不变（"不再生成"即为 true）。只认 `is_completed` 的旧前端、SDK、CLI 都能正常工作。
- C2：数据库只新增字段并提供默认值，不改、不删已有字段；迁移可以在服务运行时执行，不锁表。
- C3：接口只新增响应字段。`continue-stream` 在已有 404 场景下改为返回终止事件，这一行为变化必须保证旧前端不会卡住、不会循环报错（见 AC6）。
- C4：先发后端、再发前端。新后端搭配旧前端、旧后端搭配新前端，都不能出现新的错误。
- C5：同时兼容 Redis 和内存两种流管理器。内存版在进程重启后状态全部丢失，按"没有进行中的轮次"处理。

## 4. 设计

### 4.1 数据模型

`messages` 表新增三个字段：

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `status` | `varchar(16)` | `''` | `generating` / `completed` / `failed` / `stopped` / `interrupted`；空字符串表示旧数据，按 `is_completed` 推断 |
| `error_code` | `varchar(64)` | `''` | 机器可读的失败原因，例如 `kb_search_failed`、`model_error`、`persist_failed`、`process_lost` |
| `error_message` | `text` | `''` | 给用户看的简短说明，不含内部堆栈和敏感信息 |

- `types.Message` 增加对应字段，json 名为 `status`、`error_code`、`error_message`。
- 新增方法 `EffectiveStatus()`：`status` 非空时直接返回；为空时，`is_completed=true` 返回 `completed`，否则返回 `generating`。所有读取方都通过这个方法判断状态，不直接读字段。
- 写入规则：任何写终态的地方都同时写 `is_completed=true` 和对应的 `status`，保证约束 C1。
- 迁移文件：Postgres 写在 `migrations/versioned/000119_message_turn_status.{up,down}.sql`，SQLite 写在 `migrations/sqlite/000037_message_turn_status.{up,down}.sql`（编号以开发时的最新编号加一为准）。只加字段，不在迁移里回填数据（回填见 4.6）。

### 4.2 统一收尾

- 新增 `finalizeTurn(ctx, streamCtx, outcome)`，`outcome` 包含终态、错误码和错误说明，快速问答与 Agent 两种模式共用。
- **幂等写入**：仓储层新增 `FinalizeMessage(ctx, sessionID, messageID, status, code, msg, content…)`，SQL 条件是 `WHERE id=? AND session_id=? AND (status IN ('', 'generating')) AND is_completed=false`。已经是终态的消息不会被覆盖，避免成功路径和失败路径重复写入。
- **调用时机**：
  - 成功：`completeQuickAnswerTurn` 和 Agent 完成路径照旧，内部改为通过 `finalizeTurn` 写入 `completed`。
  - 出错：`serviceErr != nil` 且不是用户主动停止时，写入 `failed`，并带上错误码和说明，之后再发出错误事件。
  - Agent 引擎出错：引擎自己发出 `error` 事件（不带错误码），`AgentQA` 同时把错误返回给调用方，不再重复发事件。事件总线上的 `watchTurnErrors` 注册在流处理器之前（总线按注册顺序同步执行），所以先写 `failed`，客户端后收到错误帧；错误帧里的 `code` 取刚写入的错误码。之后 defer 只保存步骤和已生成的内容，保持 `failed`，不建索引、不生成追问、不抽取记忆、不发 `complete`，排队中的 steer 消息按停止处理丢弃。
  - 用户停止：沿用现有停止逻辑，同时写入 `stopped`（已生成的内容照常保留）。
  - 兜底：goroutine 最外层 `defer` 中再调用一次 `finalizeTurn(interrupted, process_lost)`。因为写入是幂等的，前面已经写过终态时，这次调用不产生任何效果；如果中途发生 panic 或漏掉了某个分支，就由它兜底。
- **完整保存也带条件**：成功和停止的完整保存（内容、步骤、引用、产物和终态一起写）走 `PersistTurnMessage`，条件是"行仍在生成，或者已经是同一个终态"。别的路径已经把这一轮写成别的终态（停服、对账、另一个副本）时不写入，内存里的消息改为数据库里的状态，也不触发成功后的附带任务。写入时 `error_code` / `error_message` 即使为空也一起写，避免 `completed` 带着旧的失败原因。
- 内存里的终态只跟随实际写入结果：`FinalizeMessage` 生效（或写库报错、需要后面的完整保存带上这个决定）时才更新；完整保存失败时恢复原值，再由 `finalizeTurn(failed, persist_failed)` 收尾，然后才发 `message_persistence` 错误帧。判断"本进程是否已决定终态"只看 `status`，不看 `is_completed`：流处理器在答案结束时就把内存里的 `is_completed` 置为 true，那时还没有写库。同一轮的终态判断和写入用 `turnMu` 串行，避免引擎 goroutine、停止和停服同时改写。
- 终态写入脱离请求的取消（`context.WithoutCancel`），但各自有上限：`finalizeTurn` 10 秒，完整保存 30 秒，避免数据库卡住时拖住停服。
- 终态写入成功后清除 live-run 标记（`ClearLiveRun`）。

### 4.3 续流自愈

修改 `ContinueStream`（[stream.go](../../../internal/handler/session/stream.go#L35)）：

1. 消息已经是终态（`EffectiveStatus()` 不是 `generating`）：返回现有的 `Incomplete message not found` 结果，同时在响应体里加上 `status`，前端据此直接展示终态。
2. 消息仍为 `generating`，并且流中有事件：保持现有逻辑（回放并继续推送）。
3. 消息仍为 `generating`，流中没有事件：
   - 查询 `GetLiveRun(sessionID)`。如果 live-run 正指向这条消息，说明轮次还活着，只是还没产生事件：保持现有的等待逻辑。
   - 如果没有 live-run，或者 live-run 指向别的消息，**并且**消息的 `updated_at` 已经超过宽限期（默认 2 分钟，防止刚创建消息、还没来得及设置 live-run 的竞态）：调用 `FinalizeMessage(interrupted, process_lost)`，然后以 SSE 方式返回**一个**错误事件（`response_type=error`、`done=true`、`data.code=turn_interrupted`、文案"本次回答已中断，可以重新提问"）后结束连接。
   - 没有超过宽限期：返回现有的 404，前端按现有逻辑处理。
   - 判断"还活着"的依据：本进程的生成中登记表（快速问答不写 live-run，只能靠它）、live-run 标记、宽限期。live-run 标记只由生成它的进程续期（每 5 分钟一次心跳，`TouchLiveRun` 按消息 id 比较后续期）；读取标记不再续期，进程被杀后标记会按 TTL 过期，不会因为续流和对账反复读取而一直存在。
   - `FinalizeMessage` 没有生效（这一轮在读和写之间已经结束）：重新读取消息，返回带实际 `status` 的 404，不声称"已中断"。

这样一来，旧前端最多看到一次错误，再次打开会话时消息已经是终态，不会再请求续流。

### 4.4 后台对账

- 新增后台任务 `TurnReconciler`，每 5 分钟执行一次。
- 多副本部署时，用 Redis `SET NX EX` 抢一把锁（键名 `{prefix}:turn-reconciler:lock`，过期时间 4 分钟），抢到的副本执行；使用内存流管理器时只有单进程，不需要加锁。
- 扫描条件：`role='assistant' AND is_completed=false AND updated_at < now() - 宽限期`，每批 200 条。逐条检查 live-run，确认没有进行中的轮次后，写入 `interrupted / process_lost`。
- 对账的宽限期默认为流 TTL（1 小时）。时间较短的情况由 4.3 的续流自愈处理，后台对账只负责清理没人打开的残留会话。
- 每轮打印一条汇总日志：扫描条数、修复条数、跳过条数。

### 4.5 优雅退出

- 进程收到 SIGTERM 时，对本进程内仍在生成的轮次逐个调用 `finalizeTurn(interrupted, process_lost)`，再退出。
- 实现顺序：先一次性取消所有轮次的生成（不等数据库），再并行写 `interrupted` 并等待写完（后面的清理会关数据库）。取消回调会给这一轮打上"停服"标记，轮次自己的 defer 看到上下文被取消时据此记为 `interrupted` 而不是 `stopped`；两边写的是同一个终态，谁先落库都一样。
- 清理钩子按注册的逆序执行。`LiveTurns` 在容器装配的最后一步（与 `BrowserSkill` 一起，`promoteFirstShutdownHooks`）提到最前，保证它先于 IM、Asynq 等后注册的钩子运行。
- 需要与 k3s 的 `terminationGracePeriodSeconds` 配合，确认 Helm 中该值不小于 30 秒（开发时检查 `helm/templates/app.yaml`）。

### 4.6 存量修复

- 一次性脚本或管理命令：把 `role='assistant' AND is_completed=false AND updated_at < 部署时间 - 1 小时` 的消息，写为 `interrupted / process_lost`。
- 执行前先跑统计 SQL，把数量记录到本文第 10 节；执行后再统计一次，确认归零。
- 部署 4.4 后台对账后，这一步实际上会自动完成；单独列出来，是为了让修复数量有据可查。
- 实现形式：管理命令 `primind-server -backfill-interrupted-turns [-dry-run] [-older-than 1h]`（复用对账的扫描与 live-run 判断，先打印修复前数量，修复后打印 `scanned / repaired / skipped / remaining`），以及纯 SQL 版本 `scripts/sql/bf03_backfill_interrupted_turns.sql`（没有镜像 shell 时用）。
- 管理命令只装配它需要的部分（`container.BuildTurnBackfillContainer`：配置、数据库、Redis、流管理器、消息仓储、对账器），不启动 HTTP、Asynq、IM、定时任务和对账循环，不会在正在服务的副本旁边接任务；退出前关闭数据库、Redis 和流管理器的连接，失败时以非零码退出。

### 4.7 前端

- 消息类型增加 `status`、`error_code`、`error_message`，读取时同样遵循"`status` 为空就按 `is_completed` 推断"的规则。
- 加载历史消息时（[index.vue](../../../frontend/src/views/chat/index.vue#L953)），只有 `EffectiveStatus()==='generating'` 的助手消息才触发续流。
- 续流时：
  - 收到 `data.code=turn_interrupted` 的错误事件：结束"正在回复"状态，把这条消息标为已中断，**不弹**全局错误提示。
  - 收到 404：不弹"流式连接失败"，按 404 响应体里的 `status` 处理：`generating`（后端还在负责这一轮，只是还没有事件）每 5 秒重试一次，最多 30 次，超过后端的宽限期；重试用完仍是 `generating` 时只停止自动重试，消息保持生成中，由后端自愈或下次加载历史决定；`completed` / `stopped` / `failed` / `interrupted`（这一轮在加载历史和续流之间已经结束）重新加载历史，显示实际保存的结果；没有 `status`（旧后端）才把消息标为已中断。其他 HTTP 错误保持现有处理。
  - 实时流里的 `error` 帧（Agent 与快速问答统一处理）：记为 `failed` 并带上 `code`，已生成的内容保留，错误文字放在 `error_message`，不覆盖答案。
- 失败、中断的消息气泡显示状态说明（失败时附上 `error_message`），并提供"重新提问"按钮，用原问题重新发起提问。没有正文的失败 / 中断消息也不能被"空段落"规则隐藏；嵌入模式下状态说明使用嵌入样式。
- IM 渠道的静默轮询逻辑保持不变。

### 6.3 集成与故障注入（本机 WSL 的 Postgres 与 Redis）

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 检索失败 | 临时把 OpenSearch 地址改成无效地址后提问 | 页面显示失败状态；刷新后不再续流 |
| 进程被杀 | 提问后在生成中途 `kill -9` 后端进程，再重启 | 宽限期后打开会话，显示已中断；或者等后台对账自动修复 |

| 滚动发布 | 在预发环境生成过程中执行 `kubectl rollout restart` | 消息最终变为已中断，不残留 `generating` |

## 7. 上线流程

1. **迁移**：T1 的迁移只加字段并设置默认值，可以在服务运行时执行。执行后检查表结构。
2. **后端**（T2～T6、T10）：部署后检查对账日志，确认第一轮的修复数量与 T8 的统计数量相近。
3. **存量修复**（T8）：如果对账已经修复完，只需再执行一次统计，确认为零。
4. **前端**（T7）：后端上线并稳定 1 天后再发布。
5. **回滚**：
   - 前端回滚：没有副作用（旧前端只认 `is_completed`）。
   - 后端回滚：新字段保留不用，不影响旧版本；已写入终态的消息，`is_completed` 都是 true，旧版本也能正确识别。
   - 迁移回滚：down 迁移删除三个字段。只有在确认不再需要时才执行。

## 9. 长期运行保障

### 10.2 8 小时时差排查结论

- **结论：不是前端重复换算时区，也不是截图电脑的时区问题，是读数据库时的时区解读问题。无需另开缺陷单。**
- 证据：
  - `messages.created_at / updated_at` 在 Postgres 中是 `TIMESTAMP WITH TIME ZONE`（`migrations/versioned/000000_init.up.sql`）；
  - 服务端 DSN 固定 `TimeZone=UTC`，GORM `NowFunc` 返回 `time.Now().UTC()`（`internal/container/container.go`），本机开发库 `SHOW timezone` 为 `Etc/UTC`。用 SQL 客户端直接查，看到的是 UTC 会话时区下的字面值：`09:38`（UTC）＝ `17:38`（北京时间）；
  - 前端 `formatMessageTimestamp` 用 `new Date(created_at)` 取绝对时间，再按浏览器本地时区格式化（`frontend/src/utils/messageTimestamp.ts`），没有任何手动偏移；接口返回的时间带 `Z` 时区标记，解析无歧义。
  - 所以截图里的 17:38 是正确的北京时间；缺陷文档中"数据库里的创建时间为 09:38（北京时间）"这句把 UTC 当成了北京时间。
- 生产复核方法（可选）：`SELECT id, created_at, created_at AT TIME ZONE 'Asia/Shanghai' FROM messages WHERE id = '77529e5c-…';` 预期第二列 `…09:38:41+00`、第三列 `17:38:41`。如果第三列不是 17:38，再回头看截图电脑的时区设置。

### 11.1 开发时的决定（对应上面的风险与待确认）

- R2：`messages` 原来没有 `is_completed` / `updated_at` 上的索引，已按建议新增部分索引 `idx_messages_generating ON messages (updated_at) WHERE is_completed = false`：Postgres 为 `000120_messages_generating_index`（`CONCURRENTLY`，单独成文件），SQLite 并入 `000037`。
- "重新提问"的实现：用原问题文本和它当时的 @提及重新发起提问；智能体和知识库使用**当前**输入栏的选择（即会话 `last_request_state` 还原出来的那套，通常就是失败时用的那套）。上传的图片和附件不会重复上传。
- 文案：失败 / 中断的状态说明按 `error_code` 用前端 i18n 本地化（`chat.turnStatus.*`、`chat.turnError.*`，六个语言都已补齐）；后端写入的 `error_message` 作为兜底显示。中断统一为"本次回答已中断，可以重新提问"。
- 实现与 spec 的两处偏差，均已在代码注释中说明：
  1. 快速问答的"兜底"不能放在 goroutine 的 defer 里：`KnowledgeQA` 返回时答案还在后台流式生成，goroutine 退出并不代表轮次结束。所以快速问答的兜底只覆盖 panic，流中途的模型错误改为监听流上的 `error` 事件（`watchTurnErrors`，现在两种模式共用）；流既没有 `Done` 也没有 `error` 就断掉的情况交给对账任务。Agent 模式仍按 spec 在 defer 末尾兜底。
  2. 增加了一个进程内的"生成中轮次"登记表（`internal/turn`）：SIGTERM 时据此收尾；对账任务跳过本进程仍在生成的消息。原因是快速问答不写 live-run 标记，只看 live-run 无法区分"正在生成"和"已死"。登记超过 2 小时（`turn.MaxTurnAge`，与停止监视器的上限一致）就不再为该轮次担保，避免流悄悄断掉、从未注销的轮次被对账永久跳过。
