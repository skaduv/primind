## 1. 根因与长期风险

1. **后端不区分失败原因。** 仓储层能区分“不存在”和“已过期”，服务层也保留了这个区别，但预览、加入、提交申请三个 handler 都把任何错误报成 404 `Invalid invite code`，连数据库错误也一样。[仓储查询](../../../internal/application/repository/organization.go#L56) · [服务层](../../../internal/application/service/organization.go#L161) · [预览](../../../internal/handler/organization.go#L617) · [加入](../../../internal/handler/organization.go#L675) · [申请](../../../internal/handler/organization.go#L727)
2. **前端拿不到错误码，也不翻译。** 三个接口封装失败时只返回 `message`，错误码被丢弃；页面优先显示后端英文原文，中文文案「邀请码无效或已过期」在这条路径上走不到。[封装](../../../frontend/src/api/organization/index.ts#L405) · [页面提示](../../../frontend/src/views/organization/OrganizationList.vue#L831)
3. **邀请码默认 7 天过期，过期后没人知道。** 管理员复制链接时不会被提醒链接已过期；成员只看到一句英文；后端不记日志。三方都无法自助发现问题。[默认 7 天](../../../internal/application/service/organization.go#L19) · [复制链接](../../../frontend/src/views/organization/OrganizationSettingsModal.vue#L1641)
4. **链接入口不容错。** 预览失败后输入框是空的；输入框不解析整条链接；未登录打开链接，登录后邀请码丢失。[链接入口](../../../frontend/src/views/organization/OrganizationList.vue#L1072) · [守卫跳转](../../../frontend/src/router/index.ts#L373)

长期运行时，第 3 点影响最大：只要空间使用默认有效期，每个空间创建 7 天后，所有已发出的链接都会失效，而且每次都要靠人工排查才能发现是过期。

## 2. 目标与非目标

**目标**

- G1：成员能看懂失败原因。过期、不存在、服务异常三种情况给出不同的中文提示，并告诉成员下一步找谁。
- G2：管理员在发出链接之前就能发现链接已过期，并一步完成「刷新并复制」。
- G3：链接入口容错。预览失败后可直接重试；粘贴整条链接也能识别；未登录打开链接，登录后回到加入窗口。
- G4：后端日志能查到每次失败的原因和脱敏后的邀请码。

**非目标**

- 不改变邀请码的生成规则、长度和默认有效期（7 天）。
- 不改变“修改有效期只影响之后刷新生成的邀请码”这一现有语义。是否让修改有效期同时作用于当前邀请码，属于产品决定，见第 11 节。
- 不改变链接域名的取法（`window.location.origin`）。环境不一致只在排查时核对，不在本期处理。
- 不改变加入和审批的授权模型。
- 未登录用户登录后需要先建工作空间（onboarding）时，本期不保证回到加入窗口。

## 3. 兼容性约束

- C1：邀请码“不存在”和“已过期”两种情况，HTTP 状态码和英文原文保持 404 `Invalid invite code` 不变，只新增业务错误码。旧前端显示的内容与现在相同。
- C2：以下两种情况的状态码会改变，属于有意修正，需要在发布说明中写明：
  - 数据库等内部错误：404 → 500 `Failed to look up invite code`。原来报成“邀请码无效”是误报。
  - 通过邀请码直接加入一个需要审核的空间：404 → 400，文案说明应改走申请接口。前端对需审核的空间本来就走申请接口，只有直接调接口或 CLI 会碰到。
- C3：新前端配旧后端时，没有新错误码，前端按状态码兜底：404 显示「邀请码无效或已过期」，5xx 和网络错误显示「预览失败，请稍后重试」，都不再显示英文原文。
- C4：登录后的返回地址只接受站内相对路径，防止被利用做开放跳转。
- C5：不涉及数据库迁移。

## 4. 设计

### 4.1 后端：错误码

在 [errors.go](../../../internal/errors/errors.go#L55) 新增一段：

```go
// Organization invite errors (2400-2499).
// HTTP status and message stay "404 Invalid invite code" for backward
// compatibility; the typed code tells clients why the lookup failed.
ErrInviteCodeNotFound ErrorCode = 2400
ErrInviteCodeExpired  ErrorCode = 2401

func NewInviteCodeNotFoundError() *AppError // 404, "Invalid invite code"
func NewInviteCodeExpiredError() *AppError  // 404, "Invalid invite code"
```

写法参照现有的 `NewModelInUseError`。

### 4.2 后端：三个接口共用的错误映射与日志

在 `internal/handler/organization.go` 中新增：

```go
// inviteLookupError maps an invite-code lookup failure to the API error
// and logs the reason with a masked code. op is preview / join / join_request.
func inviteLookupError(ctx context.Context, op, inviteCode string, tenantID uint64, err error) *apperrors.AppError
```

| 服务层错误 | 返回 | 日志级别 |
| --- | --- | --- |
| `service.ErrOrgNotFound` | `NewInviteCodeNotFoundError()` | Warn，`reason=not_found` |
| `service.ErrInviteCodeExpired` | `NewInviteCodeExpiredError()` | Warn，`reason=expired` |
| 其他 | `NewInternalServerError("Failed to look up invite code")` | Error，带原始错误 |

- 日志字段：`op`、`tenant_id`、`reason`、`invite_code`。邀请码只保留前 4 位，其余替换为 `*`（例如 `6e9b************`），再经过 `secutils.SanitizeForLog`。
- 预览、申请两个 handler 的 `GetOrganizationByInviteCode` 失败分支改为调用它。
- 加入 handler：保留现有的“成员已满”分支；新增 `errors.Is(err, service.ErrOrgPermissionDenied)` 分支，返回 400 `This organization requires approval. Use the join-request endpoint instead.`（与申请接口里的对称文案一致）；其余错误交给 `inviteLookupError`。
- 过期时是否额外返回到期时间：不返回。成员端不需要，返回反而泄露空间信息。

### 4.3 前端：接口封装保留错误码

- `previewOrganization`、`joinOrganization`、`submitJoinRequest` 的 `catch` 改为统一调用一个内部函数，返回 `{ success: false, message, code, status }`。`code` 取自 `e?.error?.code`（拦截器已把返回体展开到抛出对象上，取法与 [modelUsage.ts](../../../frontend/src/api/model/modelUsage.ts#L102) 相同），`status` 取自请求封装记录的 HTTP 状态码。
- `ApiResponse` 类型增加可选的 `code?: number` 和 `status?: number`。其他调用方不受影响。
- store 的 `join` 在失败时除了写 `error`，再写一个 `errorCode`（以及状态码），供页面映射。[store join](../../../frontend/src/stores/organization.ts#L293)

### 4.4 前端：错误文案映射与链接解析

新建 `frontend/src/views/organization/inviteCode.ts`，只放纯函数，便于单元测试：

```ts
export const INVITE_CODE_NOT_FOUND = 2400
export const INVITE_CODE_EXPIRED = 2401

// 把失败结果映射成 i18n key；不返回后端原文
export function inviteErrorKey(result: { code?: number; status?: number }, fallbackKey: string): string

// 从输入中取出邀请码：整条链接取 ?code= 或 ?invite_code=，否则返回去掉空白后的原文
export function extractInviteCode(input: string): string
```

`inviteErrorKey` 的规则：

| 条件 | i18n key | 中文文案 |
| --- | --- | --- |
| `code === 2401` | `organization.invite.codeExpired`（新增） | 邀请码已过期，请向空间管理员索取新的邀请链接 |
| `code === 2400` | `organization.invite.codeNotFound`（新增） | 邀请码无效，请核对邀请码，或向空间管理员索取新的邀请链接 |
| 无 `code` 且 `status === 404`（旧后端） | `organization.invite.invalidCode`（已有） | 邀请码无效或已过期 |
| `status >= 500` 或没有状态码（网络错误） | `organization.invite.previewFailed`（已有） | 预览失败，请稍后重试 |
| 其他 | 调用方传入的 `fallbackKey` | — |

“其他”包括成员已满、已提交过申请等已有的中文或英文提示。这些不在本期范围内，保持现在的显示方式：先用 `result.message`，为空时用 `fallbackKey`。

新增文案要补齐 6 个语言文件（zh-CN、zh-TW、en-US、ja-JP、ko-KR、ru-RU）。

### 4.5 前端：成员端加入窗口

改动集中在 [OrganizationList.vue](../../../frontend/src/views/organization/OrganizationList.vue#L831)：

- `handleInvitePreview` 失败时：用 `inviteErrorKey` 得到提示；同时把 `code` 回填到 `joinInputCode`，让成员可以直接点「查看」重试。
- `doPreviewFromInput` 先经过 `extractInviteCode`，再发起预览。输入框的说明文字「粘贴邀请链接中的邀请码」从此与行为一致，不用改。
- `confirmJoinOrganization` 的直接加入和提交申请两条失败分支，都改用 `inviteErrorKey`。邀请码在“预览成功后、点加入前”恰好过期时，也能看到「已过期」。

### 4.6 前端：管理员端复制提醒

改动集中在 [OrganizationSettingsModal.vue](../../../frontend/src/views/organization/OrganizationSettingsModal.vue#L1239)：

- 新增计算属性 `inviteCodeExpired`，判断规则与现有的剩余有效期文案相同。
- 邀请码已过期时：
  - 邀请链接和邀请码旁显示醒目的「已过期」标记（现在只在剩余有效期一栏显示文字）。
  - 点「复制链接」或「复制邀请码」时，不直接复制，弹出确认框：「当前邀请码已过期，复制出去也无法使用。」按钮为「刷新并复制」和「取消」。
  - 「刷新并复制」：调用现有的 `refreshInviteCode`，成功后再复制新的链接或邀请码；刷新失败就停止，不复制。旧码本来就已过期，刷新不会让任何有效链接失效。
- 未过期时，复制行为与现在相同。

### 4.7 前端：未登录打开链接后回到原处

- 路由守卫中“未登录、恢复会话失败、跳转登录页”的分支，改为跳转 `{ path: '/login', query: { redirect: to.fullPath } }`。守卫里共有两处跳登录页（[第 315 行](../../../frontend/src/router/index.ts#L315)、[第 373 行](../../../frontend/src/router/index.ts#L373)），开发时确认两处是否都属于这种情况（结论见 §10.2）。
- 新建纯函数 `safeRedirect(value: unknown): string | null`：只接受以单个 `/` 开头的站内路径；拒绝 `//`、`/\`、带协议的地址，以及指向 `/login`、`/register` 的地址。
- 登录页登录成功后，如果 `safeRedirect(route.query.redirect)` 有值且用户已有有效工作空间，就跳到该地址；否则保持现在的默认跳转。
- OIDC 登录会离开本站。发起 OIDC 前把返回地址写入 `sessionStorage`，回调成功后读取并清除。开发时确认 OIDC 回调落在哪个页面，结论写入第 10 节（见 §10.3）。

## 7. 上线流程

1. 后端（T1、T2）先上线。旧前端看到的提示与现在相同（C1）；内部错误和“需审核”两种情况的状态码变化见 C2。
2. 前端（T3～T7）随后上线。T7 可以独立上线。
3. 不涉及数据库迁移，不需要功能开关。
4. 回滚：直接回退版本，没有数据副作用。
5. 上线后，把临时处理步骤（缺陷文档“临时处理”一节）同步给空间管理员，处理已经过期的存量链接。

## 8. 验收标准

| 编号 | 场景 | 预期 | 验证方式 |
| --- | --- | --- | --- |
| AC1 | 邀请码已过期，通过链接、输入邀请码、点「加入」、点「申请加入」四种方式 | 都提示「邀请码已过期，请向空间管理员索取新的邀请链接」；中文界面不出现英文原文 | 手工 |
| AC2 | 邀请码不存在或已被刷新 | 提示「邀请码无效，请核对邀请码，或向空间管理员索取新的邀请链接」 | 手工 |
| AC3 | 通过链接进入且预览失败 | 输入框中带有该邀请码，直接点「查看」可以重试 | 手工 |
| AC4 | 在输入框粘贴整条邀请链接 | 能正常预览 | 手工 |
| AC5 | 管理员复制已过期的链接或邀请码 | 出现确认框；「刷新并复制」后剪贴板中是新链接，新链接可用 | 手工 |
| AC6 | 未登录打开邀请链接 | 登录后回到加入窗口；`redirect` 指向站外地址时被忽略 | 手工 |
| AC7 | 预览时数据库不可用 | 提示「预览失败，请稍后重试」，接口返回 500 | 本机手工 |
| AC8 | 失败日志 | 后端日志可查到 `op`、`reason`、脱敏后的邀请码 | 日志 |
| AC9 | 旧前端 + 新后端 | 不存在和已过期两种情况，提示与现在一致 | 预发手工 |
| AC10 | 新前端 + 旧后端 | 预览失败提示「邀请码无效或已过期」，不出现英文 | 预发手工 |
| AC11 | 回归测试 | 第 6.1、6.2 节命令全部通过，附命令输出 | 测试日志 |

## 9. 长期运行保障

- 以后邀请码新增失败原因（例如“空间已停用”）时，只需在 2400 段新增一个错误码、在 `inviteLookupError` 和 `inviteErrorKey` 各加一个分支，三个接口和两个页面会同时生效。
- 后端日志中 `reason=expired` 的次数可以作为参考指标。上线一段时间后如果次数仍然较多，说明 7 天默认有效期偏短，再按第 11 节的待确认项讨论是否调整。

### 10.3 OIDC 回调落在哪个页面，返回地址如何传递

- **回调落点：`App.vue`，不是 `Login.vue`。** 后端 `GET /api/v1/auth/oidc/callback` 处理完 IdP 回跳后，把浏览器重定向到前端根路径并带 hash（`#oidc_result=…` 或 `#oidc_error=…`）。[App.vue](../../../frontend/src/App.vue#L132) 挂载时 `handleGlobalOIDCCallback()` 消费这个 hash，成功后调用 [`persistOIDCLoginResponse()`](../../../frontend/src/App.vue#L102)，原来在这里固定跳知识库列表或引导页。
- **传递方式：** [`Login.vue`](../../../frontend/src/views/auth/Login.vue#L637) 的 `handleOIDCLogin` 在 `window.location.href = authorizationURL` 之前调用 `stashPendingLoginRedirect(route.query.redirect, sessionStorage)`，存进 `sessionStorage` 的 `primind_login_redirect`（与已有的 `primind_pending_invite_token` 同一位置、同一种“跳走前暂存、回来后消费”的用法）；`App.vue` 在 `persistOIDCLoginResponse()` 末尾调用 `consumePendingLoginRedirect(sessionStorage)`，读后即清，读出时再过一次 `safeRedirect`，然后交给 `postLoginTarget()`。
- 密码登录路径也把暂存值当兜底：OIDC 失败回到登录页时，URL 上的 `redirect` 已被 `clearOIDCCallbackState('/login')` 清掉，这时改用密码登录仍能回到原处。
- **没有实测 OIDC 往返**：本机没有可用的 IdP。这条路径由单测覆盖（`safeRedirect.test.ts` 的暂存 / 消费用例，以及对 `Login.vue`、`App.vue` 的源码断言）。请在预发环境用真实 IdP 走一遍“未登录打开邀请链接 → OIDC 登录 → 回到加入窗口”。

### 10.4 `ApiResponse` 类型定义位置，增加字段后是否影响其他调用方

- 定义在 [`frontend/src/api/organization/index.ts`](../../../frontend/src/api/organization/index.ts#L185)（`export interface ApiResponse<T>`），只在该模块内导出；store 和页面都从 `@/api/organization` 引用。
- 新增的是两个可选字段 `code?: number`、`status?: number`，只由失败的三个接口封装写入。成功分支的 `response as unknown as ApiResponse<T>` 不受影响；其他调用方只读 `success` / `data` / `message`。`npm run type-check`（`vue-tsc --build`）通过。
- 失败结果的归一化函数 `requestFailure` 单独放在 `frontend/src/api/organization/requestFailure.ts`。原因：它不能依赖 `@/utils/request`（会带进 axios、i18n 和 Vite 环境变量），否则没法单测；`index.ts` 从它导入，不对外再导出。

### 10.5 实现与 spec 的出入（开发时的决定）

1. **4.4 / 4.5：页面不再自己判断“是否显示后端原文”。** 实现在 `inviteErrorKey` 之外新增了两个纯函数：`knownInviteErrorKey(result)`（已知失败返回 key，否则 `null`）和 `inviteFailureMessage(result, fallbackKey, t)`。原因见 §12.3：端到端复测时发现，预览接口 500 的返回体带有业务码 1007 和英文原文 `Failed to look up invite code`，如果用“`inviteErrorKey` 的结果是否等于 `fallbackKey`”来判断，5xx 会被当成“其他”而显示英文，与 AC7、C3 不符。现在“已知失败”和“兜底”分开判断，页面里没有任何映射逻辑。
2. **4.4 表格里的“无 `code` 且 `status === 404`”：实现为“`code` 不是 2400 / 2401 且 `status === 404`”。** 旧后端的 404 带的是通用码 1003，并不是没有 `code`。
3. **`extractInviteCode`：** 只有输入含 `?`、且能解析出非空的 `code` 或 `invite_code` 时才取参数（`code` 优先）；其余情况原样去掉空白后返回，包括 `?code=` 为空和无法解析的文本。
4. **4.5：输入框 `maxlength` 从 32 放宽到 512。** 整条链接（`http://主机/join?code=…`）超过 32 个字符，不放宽的话粘贴进来就被截断。
5. **4.2 脱敏：** 长度不超过 4 的输入整体打码，不保留任何原字符；长度大于 4 的保留前 4 位。spec 只写了后一种。
6. **4.2 日志：** “其他”这一行的 `reason` 取 `internal`。spec 的表只给了前两种的 `reason`，而 AC8 要求每次失败都能查到 `reason`。另外，加入接口“需审核”分支在 handler 里记一条 Warn；“成员已满”分支沿用改造前的 Errorf。
7. **4.2 写法：** 这三个 handler 里改到的 `c.Error(...)` 写成 `_ = c.Error(...)`，是 golangci-lint 的 errcheck 对改动行的要求，仓库里其他 handler 已经是这个写法。
8. **swagger：** 三个接口的 `@Failure` 注解按新的状态码补齐后，用 `make docs` 的同一条命令重新生成了 `docs/docs.go`、`swagger.json`、`swagger.yaml`。生成结果里还带上一处与本期无关、但 `main` 上已经存在的漂移（向量库删除接口的描述文案），属于把文档和注解对齐。
9. **4.6 管理员端文案：** 确认框标题新增 `organization.settings.inviteCodeExpiredTitle`；「取消」复用 `common.cancel`；「已过期」标记复用 `organization.settings.remainingValidityExpired`。`refreshInviteCode` 改为返回是否刷新成功，供「刷新并复制」决定是否继续复制。
10. **4.7 `safeRedirect` 比 spec 多拒绝两类输入：** 路径中含反斜杠；第二个字符是制表符或换行符。浏览器解析 URL 时会先删掉这些字符，`/<TAB>/evil.com` 会变成 `//evil.com`。`/login`、`/register` 的比较忽略大小写和结尾斜杠（vue-router 默认不区分大小写）。

### 10.6 复测中发现的既有问题（不在本期范围，建议另开单）

1. **访问日志仍然打印完整的邀请码。** `middleware/logger.go` 的访问日志会输出 `path=/api/v1/organizations/preview/<完整邀请码>` 和 `request_body={"invite_code":"<完整邀请码>"}`。本期新增的应用日志已经脱敏，但同一次请求的访问日志里还是明文，G4 的“脱敏”目前只对新增的那一行成立。建议对这三个路径的访问日志做同样处理（路径参数和请求体打码，或不记录这两个路由的请求体）。
2. **数据库整体不可用时，请求到不了 handler。** 认证中间件对每个请求都要查库校验 token（日志：`[auth] bearer token rejected: look up token: …`）。数据库一停，所有已登录请求直接 401，前端接着刷新 token 失败并把用户登出。所以 §6.3 第 8 步“停掉数据库后预览”在界面上看不到 500 和「预览失败」，看到的是被登出。这是既有行为。handler 的 500 分支改用两种方式验证：单测（服务层返回其他错误 → 500），以及端到端故障注入（把 `organizations` 表临时改名，只让邀请码查询失败，认证不受影响），见 §12.3。
3. **新用户首次进入页面会弹出「欢迎使用 Primind」引导，遮罩挡住加入窗口的按钮**（点「跳过引导」即可）。不是本期的问题，但手工走查时要先处理它。

## 11. 风险与待确认
