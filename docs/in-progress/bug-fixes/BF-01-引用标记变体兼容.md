## 1. 根因与长期风险

后端用严格的正则解析模型的自由文本输出，只认 `<ref id="cN"/>`。本地模型遵守格式的能力不稳定，会写成 `[ref id="c2"]` 之类的变体，后端识别不了，就原样下发。

长期运行时有两个放大因素：

1. **换模型就会出新变体。** 每接入一个新模型都可能重新踩坑，现在没有任何手段提前发现。
2. **出错的历史消息永久坏掉。** cN 到文档的映射只在当次请求内有效，答案存库后映射就没了，事后无法再把残留标记还原成引用卡片。

## 2. 目标与非目标

**目标**

- G1：后端把已知的方括号变体统一展开成引用卡片，流式输出过程中不闪现半截标记。
- G2：前端兜底，任何残留的 `ref id=` 文本都不展示给用户，已经存库的历史消息也包括在内。
- G3：能按模型统计"未展开的引用"数量，换模型时可以用这个数据做验收。
- G4：建立真实模型输出的回归样本，新增变体时只改一张规则表。

**非目标**

- 不尝试把历史消息里的残留标记还原成引用卡片（映射已丢失，做不到）。
- 不改动引用卡片 `<kb/>`、`<web/>` 的对外格式。
- 不在本期引入约束解码或结构化输出（列为后续可选项）。

## 3. 兼容性约束

- C1：对外的 `<kb .../>`、`<web .../>` 格式和属性不变，前端、SDK、IM 渠道不受影响。
- C2：普通方括号文本必须原样保留，包括 `[1]`、Markdown 链接 `[文字](url)`、`【注】`、`array[i]`。
- C3：未登记的编号和 `dN`、`bN` 句柄仍按现有规则删除（失败即关闭，不泄露内部句柄）。
- C4：前端兜底只去掉标记，不改动其余文本；对不含残留标记的消息，渲染结果逐字节不变。

## 4. 设计

### 4.1 后端（已实现，单元测试通过）

- `bracketRefRE` 识别 `[ref id="cN"]`、`【ref id="cN"】`、id 不带引号、中文引号、带 `/` 的写法，只接受 `[cwdb]` 加数字形式的 id。`ExpandText` 开头先统一改写成标准写法，再走原有校验。[citations.go](../../../internal/modelcontext/citations.go)
- 流式展开器遇到 `[` 或 `【` 时也开始缓冲；缓冲上限 64 字节，超过仍未闭合就按普通文本放行；流结束时残留的半截引用标签直接丢弃。
- 提示词补充一条：始终使用尖括号写法。

### 4.2 后端：规则集中（新增）

- 把变体规则整理成一张带注释的表（变量或小结构体切片），注明每条变体首次出现的模型和日期。以后新增变体只改这张表和对应测试。

### 4.3 前端兜底（新增）

- 在 [citationMarkdown.ts](../../../frontend/src/utils/citationMarkdown.ts) 增加 `stripResidualRefMarkers(content)`：删除 `<ref id=…/>`、`[ref id=…]`、`【ref id=…】` 三类残留标记，id 规则与后端一致。
- 在聊天 Markdown 的预处理链里，放在 `<kb>`、`<web>` 处理**之前**调用，历史消息和流式消息都经过这一步。
- 流式过程中，`stripIncompleteCitationTag` 同样要隐藏 `[ref`、`【ref` 开头的未闭合尾巴。

### 4.4 可观测性（新增）

- 回答收尾时（快速问答和 Agent 两条路径都要覆盖），统计最终文本里被兼容规则改写的变体数和被丢弃的半截标记数。数量大于 0 时打一条结构化日志，字段包括 `model_id`、`variant`（变体类别）、`count`、`session_id`、`message_id`。
- 后端代码里目前没有 Prometheus 之类的指标出口，本期只打结构化日志，不为此新建监控设施。以后接入指标时，再按 `model`、`variant` 两个维度加计数器。

### 4.5 回归样本库（新增）

- 新建 `internal/modelcontext/testdata/model_outputs/`，每个文件存一段真实的模型原始输出（脱敏），文件头注明模型、日期、预期展开结果。
- 新增表驱动测试，遍历目录逐个断言展开结果。本次缺陷里 `qwen3.8-27b-bf16` 的那段输出作为第一个样本。

## 7. 上线流程

1. T1～T5 合并到同一个分支，提交时只包含本 spec 涉及的文件（主工作区还有大量无关改动，提交时逐个文件挑选）。
2. 前后端可以同时发布，没有先后要求：只发前端，历史消息就不再显示残留；只发后端，新回答就会正确展开。

4. 回滚：直接回退版本即可，没有数据副作用。

## 9. 长期运行保障

- **换模型时：** 先用模型跑 20 个带引用的问题，查看 4.4 的日志；有新变体时，把样本加进样本库，再在规则表里加一条。
- **定期查看：** 每周看一次变体日志的数量，按模型分组。某个模型的变体比例明显上升时，评估是否需要调整提示词或换模型。
- **后续可选：** 推理服务支持约束解码时，可以直接约束引用格式，从源头消除变体。

## 10. 风险与待确认

- R1：规则过宽可能误伤正常文本。已通过只接受 `[cwdb]` 加数字形式的 id 来控制，样本库也会持续覆盖。
- R2：64 字节的缓冲上限如果偏小，会导致超长写法被当作普通文本放行。目前已知的变体都在 30 字节以内，样本库出现超长写法时再调整。
- R3：样本库要存真实的模型输出，入库前必须去掉制度原文以外的个人信息和内部编号。

### 11.4 与 spec 不一致或需要知道的地方

- **日志条数：** 4.4 写的是「打一条结构化日志」。实现是每个变体一条，各自带 `variant` 和 `count`，这样按模型、按变体聚合时不用再解析字段。字段名与 spec 一致。
- **半截标记的变体名：** 尖括号写法的半截记为 `truncated_angle`，方括号写法的记为 `truncated_bracket`。流正常结束时的 Flush 不计数。
- **样本 001 的来源：** 缺陷报告里逐字摘录的三行原文（c2、c9、c15、c22 四处引用）。完整回答没有留存，本地库里也没有这条会话，所以样本只有这三行，文件头已注明。接入新模型后拿到完整输出时，再补一个样本。
- **规则表里只有 1 行是实际观察到的**（`square_double_quoted`，qwen3.8-27b-bf16，2026-11-23），其余 7 行是预防性登记，首次出现的模型和日期留空。
- **流式展开器多容忍了一种写法：** 开括号后面带空白（`[ ref id="c1"]`）。规则表本来就这样接受，之前流式展开器遇到这种写法会原样放行，现在和整段展开保持一致。
- **前端多改了两处：** 会话导出（`sessionMarkdown.ts`）和「加入知识库」（`stripCitationTagsForMarkdown`）也去掉了残留标记，属于 G2「任何残留都不展示」的范围，但不在 4.3 列出的调用方里。
- **主工作区未动：** `docs/bug/` 和 `docs/in-progress/` 在主工作区仍是未跟踪文件，内容是更新前的版本；工作树里是更新后的版本。
